# 反代镜像的构建与部署

改完 `kiro-rs-src/` 里的代码后，把它变成本机正在跑的服务，全过程在这里。
主要给 agent 照着执行，人工执行也是同一套命令。

## 三个位置先分清

| 位置 | 是什么 |
|---|---|
| `~/cache/AI/kiro-rs/kiro-rs-src/` | 源码，即本目录的上一级。改代码在这里 |
| `~/kiro-rs/docker-compose.yml` | 部署声明。**不在本仓库里**，改 image tag 在这里 |
| `~/kiro-rs/config/` | 运行时配置与凭据，挂载进容器。**含真实密钥，别读出明文、别进 git** |

源码和部署目录是分开的：仓库只管构建，`~/kiro-rs/` 管这台机器上怎么跑。

## 流程

### 1. 本地先验证，别直接构建镜像

镜像构建里的 Rust 编译要花 2 分半，编译错误留到那时候发现太浪费。

```bash
cd ~/cache/AI/kiro-rs/kiro-rs-src
cargo check --all-targets          # Rust 侧
cd admin-ui && pnpm build          # 前端侧（tsc -b 会做类型检查）
```

前端有改动时 `pnpm build` 是必须的，不只是为了检查类型 —— 见下面「dist 的坑」。

`cargo test` 应全绿（235 passed，其中 `anthropic::converter` 45 个）。若出现
`UnsupportedModel` 失败，说明测试里的模型名落后于 `map_model` 的白名单，
把测试改成白名单内的名字即可。

### 2. 构建镜像

```bash
cd ~/cache/AI/kiro-rs/kiro-rs-src
docker build -t kiro-rs:<tag> .
```

**tag 用改动内容命名，不要用 `latest`。** 现有历史是
`token-stats`、`used-credits`、`auto-balance` 这种风格 —— 一眼能看出这镜像装的是哪次改动，
回滚时才知道该退回哪个。`latest` 会让「当前跑的到底是哪版代码」无从查证。

Dockerfile 是三阶段的：`node:22-alpine` 构建前端 → `rust:1.92-alpine` 编译 →
`alpine:3.21` 装成品，最终镜像约 16MB。**前端在镜像内部重新构建**，
不依赖你本地的 `admin-ui/dist`。

首次构建约 3-4 分钟；只改前端时 Rust 层命中缓存，约 1 分钟。

### 3. 探活，别拿生产容器试

新镜像先用临时容器在**另一个端口**跑起来，确认没问题再碰正在服务的容器：

```bash
docker run --rm -d --name kiro-rs-smoke \
  -p 127.0.0.1:12899:12888 \
  -v ~/kiro-rs/config/:/app/config/:ro \
  kiro-rs:<tag>

sleep 4 && docker logs kiro-rs-smoke 2>&1 | tail -15
```

配置挂载加了 `:ro` —— 探活容器不该写生产凭据文件。

验证要点：日志里有「可用 API」清单且无 panic；然后验本次改动的实际效果，
例如接口新字段：

```bash
KEY=$(python3 -c "import json;print(json.load(open('$HOME/kiro-rs/config/config.json'))['adminApiKey'])")
curl -s -H "Authorization: Bearer $KEY" http://127.0.0.1:12899/api/admin/credentials | python3 -m json.tool | head -30
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:12899/admin   # 期望 200
```

改了前端就再确认页面引用的是新产物（哈希应与 `pnpm build` 输出一致）：

```bash
curl -s http://127.0.0.1:12899/admin | grep -o 'index-[A-Za-z0-9]*\.js'
```

验完拆掉：`docker stop kiro-rs-smoke`（带 `--rm`，停止即自动删除）。

### 4. 切换生产容器

**这一步会中断服务几秒，且改的是仓库外的部署文件。执行前先跟用户确认。**

```bash
cd ~/kiro-rs
cp docker-compose.yml "docker-compose.yml.bak-before-<改动名>-$(date +%Y%m%d-%H%M%S)"
# 把 image: 改成新 tag（Edit 工具改，或 sed -i '')
docker compose up -d
```

备份文件名带上改动名和时间戳，是这个目录既有的习惯，照着做。

容器由 compose 管理（`container_name: kiro-rs`，`restart: unless-stopped`），
所以用 `docker compose up -d` 而不是 `docker run` —— 后者会丢掉端口绑定、
挂载和重启策略。

### 5. 确认线上正常

```bash
docker ps --filter name=kiro-rs --format '{{.Names}} {{.Image}} {{.Status}}'
KEY=$(python3 -c "import json;print(json.load(open('$HOME/kiro-rs/config/config.json'))['adminApiKey'])")
curl -s -o /dev/null -w "admin API: %{http_code}\n" -H "Authorization: Bearer $KEY" \
  http://127.0.0.1:12888/api/admin/credentials
docker logs kiro-rs 2>&1 | grep -iE "error|panic" | head
```

再核一次容器实际用的镜像 ID 与构建输出一致，避免 tag 指向了别的层：

```bash
docker inspect kiro-rs --format '{{.Config.Image}} -> {{.Image}}'
```

凭据的 `successCount` 等状态存在挂载的配置目录里，重建容器不会丢。

`/v1/models` 返回 401 是正常的，那是需要 API Key 的业务接口。

## 回滚

改回上一个 tag 重跑即可，旧镜像通常还在本地：

```bash
cd ~/kiro-rs
sed -i '' 's|image: kiro-rs:<新>|image: kiro-rs:<旧>|' docker-compose.yml
docker compose up -d
```

所以**别急着删上一个可用镜像**，等新版稳定几天再清。

## 几个已经踩过的坑

**dist 的坑。** `admin-ui/dist` 被 gitignore（是构建产物），但 `rust-embed` 在
**编译期**就要读它。所以新克隆的仓库直接 `cargo build` 会失败，报
`function or associated item 'get' not found for this struct` —— 这不是代码坏了，
是缺 dist。先 `cd admin-ui && pnpm install && pnpm build`。
`docker build` 不受影响，Dockerfile 内部会自己构建前端。

**Cargo.lock 的坑。** 根 `.gitignore` 有 `*.lock` 规则会吞掉它，已加
`!kiro-rs-src/Cargo.lock` 例外。二进制项目必须锁依赖，别把这条例外删了。

**上游已断。** 本目录是 `hank9999/kiro.rs` 的 fork 拷贝，移入单仓时断开了 git 关联。
上游有更新只能手工 diff 对，`git pull` 拿不到。

## 清理

```bash
docker images | grep kiro-rs              # 先看有哪些
docker rmi kiro-rs:<旧tag>                # 逐个删，别用 prune 一把梭
```

删镜像不可逆（本地没有 registry 备份），但都能从源码重新构建。
`docker system df` 能看到可回收空间；build cache 用
`docker builder prune` 清，只影响下次构建速度，不动镜像。

**别碰 `172.30.10.185:15000/*` 的镜像**，那是公司内网 registry 拉的构建基础镜像，
删了要连内网才能重拉，与本项目无关。

## 账号库模式：由 proxy-rs 拉起（取代 Docker 部署）

启用后 kiro-rs 不再跑在 Docker 里，而是作为 proxy-rs 的子进程运行，两者一起启动、一起退出。
账号、凭据、额度、统计都存在共享 SQLite（默认 `~/kiro-rs/data/accounts.sqlite3`），
kiro-rs 是唯一刷新 token、查额度的一方；proxy-rs 只写昵称、分组、标签。设计见改造方案 §0。

### 切换步骤（动生产，逐步确认）

1. 构建带 kiro-rs 的 App：`cd proxy-rs && npm run dist:current`（`build:mac:current` 会先跑
   `scripts/build-kiro-rs.sh`，把二进制放进 App 的 `Contents/Resources/kiro-rs`）。
2. 退出正在运行的 proxy-rs，停掉容器：`cd ~/kiro-rs && docker compose down`。
   迁移期间不能有任何进程在刷新这些 token。
3. 预览迁移（只读）：
   `"/Applications/Proxy RS.app/Contents/MacOS/Proxy RS" --migrate-account-db`
   输出关联数、待导入数、无法导入与冲突条目。
4. 执行迁移：同一命令加 `=apply`，即 `--migrate-account-db=apply`。它会先把 electron-store 文件、
   `credentials.json`、`kiro_stats.json` 备份到 `~/kiro-rs/data/migration-backup-*/`，
   然后建库并写入 `userData/account-db.json`（enabled=true）。原文件不改、不删。
5. 正常打开 proxy-rs：它会拉起 kiro-rs（强制只监听 `127.0.0.1`，配置里的 `0.0.0.0` 被覆盖），
   并把"启动后导入"的账号交给 kiro-rs。12888 仍被占用时拒绝启动并退避重试。
6. 确认：Admin 页面 `http://127.0.0.1:12888/admin` 只列号池里的账号；proxy 账号列表完整；
   `docker ps` 里没有 kiro-rs。

### 回滚

1. 退出 proxy-rs。
2. `"/Applications/Proxy RS.app/Contents/MacOS/Proxy RS" --rollback-account-db`：库里的最新凭据写回
   electron-store，并在 `~/kiro-rs/config/` 生成 `credentials.rollback-*.json`（号池账号，保留 ID），
   `account-db.json` 改回 enabled=false。
3. 用那份 rollback 文件替换 `credentials.json`（先备份原文件）后 `docker compose up -d`。
   不要用迁移前的备份：token 在账号库模式下可能已经轮换，旧备份里的 refresh token 会失效。

### 号池与凭据归属

账号库里的每个账号都由 kiro-rs 刷新 token、查额度，但只有**入池**的账号才接反代请求。

- proxy 账号卡片上原来的"推送到反代"按钮变成号池开关：云图标常亮表示在池中，再点一次移出。
- Admin 页面默认只列号池中的账号；头部"仅号池 / 全部账号"可以看到库里其它账号并把它们加入号池。
- Admin 的"彻底删除"会把账号从库里删掉，proxy 列表也会消失，且不能用同一账号 ID 重新导入；
  只想停止接单请用"移出号池"。
- 凭据（refresh token / client 信息 / region / 首选端点）由 kiro-rs 独占写入，proxy 的编辑对话框
  里这些字段是只读的；换凭据请重新登录该账号。
- proxy 侧给账号绑定的出口代理会同步给 kiro-rs；解绑时只清除 proxy 自己设过的那份，
  迁移自 `credentials.json` 的账号自带代理保留。

### 联调

`PROXY_RS_USER_DATA_DIR=/tmp/xxx` 启动 proxy-rs 会使用独立的 userData（配置、单实例锁都隔离），
可以在正式版运行时起第二个实例验证；配合一份测试用的 kiro-rs `config.json`（端口换掉，
`proxyUrl` 指向本地不存在的端口即可阻止上游请求）写进 `/tmp/xxx/account-db.json`。
