# KSK 抢号下游接口契约

抢号器（Proxy RS 的「抢号监控」页）在自动下单模式下会调用你实现的两个本地接口。
本文是权威契约；抢号器侧的实现见 `src/main/kskHunter/downstreamClient.ts`。

## 总览

| 方法 | 路径            | 时机       | 作用                                            |
| ---- | --------------- | ---------- | ----------------------------------------------- |
| GET  | `/need-account` | **下单前** | 问你现在要不要号。回 `false` 就不下单，不花钱。 |
| POST | `/ksk`          | 验活通过后 | 把抢到的 KSK 交付给你。                         |

两个接口都在同一个 base 地址下，base 由用户在 UI 里配置（默认 `http://127.0.0.1:12889`）。
base 可以带路径前缀，例如配 `http://127.0.0.1:12889/hooks`，实际请求就是
`http://127.0.0.1:12889/hooks/need-account`。

## 鉴权

两个接口都带同一个头：

```
x-api-key: <用户在 UI 里配置的 Key>
```

**必须校验这个头**。不匹配时返回 `401`。原因是这两个接口一个能触发真实花钱、
一个会收到可直接调用上游的凭据，本机其他进程也能访问 loopback 端口。

比较时用定长比较（`crypto.timingSafeEqual`）而不是 `===`，避免时序侧信道。

## 传输安全

抢号器只在以下两种情况发起请求，否则直接报错拒绝：

- `http://` + hostname 是 `127.0.0.1` / `localhost` / `::1`
- `https://` + 任意 hostname

也就是说明文 HTTP 只对 loopback 放行。要部署到别的机器上就必须上 HTTPS，
否则 KSK 会以明文过网络。

请求不走系统代理（抢号器对下游用直连 dispatcher），所以开着全局代理也不影响。

## GET /need-account

### 请求

```http
GET /need-account HTTP/1.1
Host: 127.0.0.1:12889
Accept: application/json
Content-Type: application/json
x-api-key: your-secret-key
```

无请求体、无 query 参数。

### 响应

```json
{ "need": true }
```

| 字段   | 类型    | 含义                                                          |
| ------ | ------- | ------------------------------------------------------------- |
| `need` | boolean | `true` = 现在要号，抢号器会去下单；`false` = 不要，跳过本次。 |

`need` 也接受 `"true"`（字符串）和 `1`（数字），但**建议就用 boolean**。
字段缺失、类型不认识、或值为 `false` 一律按「不要号」处理。

### 语义要点

这个接口**每 3 秒可能被调一次**（只要有链接检测到有货），所以：

- 必须**快**。抢号器超时按 UI 里的「请求超时」配置（默认 10 秒），
  但你回得慢就等于把抢单机会让给别人。查内存计数器，别查数据库大表。
- 必须**无副作用**。它是 GET，不要在这里扣配额、写日志表、发通知。
  抢号器可能问了却没抢到（被别人抢先、下单失败），你不能假设问一次就一定会收到一个号。
- 回 `true` 后**不要预扣库存**。真正的交付信号是 `POST /ksk`，不是这个接口。

### 错误响应

非 2xx 会被抢号器当作「问不出来」，本轮**不下单**（保守策略，宁可错过也不白买）。

## POST /ksk

### 请求

```http
POST /ksk HTTP/1.1
Host: 127.0.0.1:12889
Accept: application/json
Content-Type: application/json
x-api-key: your-secret-key

{
  "key": "ksk_AbCdEf0123456789",
  "region": "eu-central-1"
}
```

| 字段     | 类型   | 说明                                                       |
| -------- | ------ | ---------------------------------------------------------- |
| `key`    | string | Kiro API Key，`ksk_` 前缀 + 字母数字。抢号器已校验过格式。 |
| `region` | string | AWS 区域，形如 `eu-central-1` / `us-east-1`。              |

抢号器只在**验活通过**后才推送：它会先拿这个 key 调一次上游 usage 接口，
调不通就标记 `dead_key` 并且**不会**推给你。所以你收到的号在推送那一刻是可用的。

### 响应

```json
{ "ok": true }
```

| 字段 | 类型    | 含义                                                  |
| ---- | ------- | ----------------------------------------------------- |
| `ok` | boolean | `true` = 已接收并落库。**只有 `true` 才算交付成功。** |

**关键**：HTTP 200 但 `ok` 不为 `true`，抢号器视为失败并会重试。
这是有意设计的——避免你的接口返回 200 但内部落库失败时，号被静默丢掉。

### 重试语义

推送失败（网络错误、非 2xx、`ok` 不为 `true`）后，抢号器按指数退避重试：

| 第几次失败 | 距下次重试                         |
| ---------- | ---------------------------------- |
| 1          | 5 秒                               |
| 2          | 10 秒                              |
| 3          | 20 秒                              |
| 4          | 40 秒                              |
| 5          | 80 秒                              |
| 6          | 不再重试，标记 `failed` 待人工处理 |

也就是最多推 6 次，总跨度约 2.5 分钟。抢到的号在推送前已经落盘加密保存，
应用重启后待推送队列会继续跑，不会因为你的服务临时挂掉就丢号。

### 幂等要求 ⚠️

**必须按 `key` 做幂等。** 重试会导致同一个 `key` 被推送多次，典型场景：
你落库成功了但响应在网络上丢了，抢号器收不到 `ok` 就会再推一次。

正确做法是把 `key` 当唯一键：已存在就直接回 `{ "ok": true }`，不要报错、
不要插重复行。参考实现里用 `Map` 按 key 去重，生产环境上数据库唯一索引。

### 错误响应

| 状态码 | 场景                         | 抢号器行为                            |
| ------ | ---------------------------- | ------------------------------------- |
| 400    | `key` 或 `region` 格式不合法 | 重试（重试也会失败，最终标 `failed`） |
| 401    | `x-api-key` 不匹配           | 重试；请去 UI 里改 Key                |
| 5xx    | 你这边内部错误               | 重试                                  |

错误响应体会被抢号器截断到 300 字符并脱敏后写进 UI 的错误提示。
**不要在错误信息里回显完整的 `key`** —— 抢号器会把 `ksk_xxx` 替换成 `ksk_••••`，
但你自己的日志也别记明文。

## 交互时序

```
抢号器                                        你的下游
  │
  │  每 3 秒并行查所有启用链接的库存
  │
  ├─ 发现有货，区域命中白名单
  │
  ├──────── GET /need-account ──────────────────▶
  │◀─────── { "need": false } ───────────────────┤   不要号 → 到此结束，不花钱
  │                                              │
  │◀─────── { "need": true } ────────────────────┤   要号 ↓
  │
  ├─ POST 商品站点下单接口（真实花钱）
  ├─ 从下单响应里提取 ksk_
  ├─ 落盘加密保存（此后崩溃也不丢号）
  ├─ 调上游 usage 接口验活
  │     └─ 验活失败 → 标 dead_key，不推送，到此结束
  │
  ├──────── POST /ksk { key, region } ──────────▶
  │◀─────── { "ok": true } ──────────────────────┤   交付完成
  │
  │◀─────── 失败 / ok 不为 true ─────────────────┤
  └─ 指数退避重试，最多 6 次
```

## 实现清单

- [ ] 校验 `x-api-key`，用定长比较，不匹配回 401
- [ ] `GET /need-account` 快速返回 `{ need: boolean }`，无副作用
- [ ] `POST /ksk` 按 `key` 幂等，重复推送回 `{ ok: true }`
- [ ] 落库成功后才回 `ok: true`
- [ ] 日志里不记 `key` 明文
- [ ] 只监听 loopback（`127.0.0.1`），或者上 HTTPS

参考实现见 `server.mjs`，自测脚本见 `selftest.mjs`。
