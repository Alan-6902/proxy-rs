# 反代的构建与部署

kiro-rs 已不再跑在 Docker 里（2026-09-29 切换）。它被打进 proxy-rs 的 App，
由 proxy-rs 作为子进程拉起，两者一起启动、一起退出；账号都存在共享 SQLite 账号库里。
设计见改造方案 §0，切换与回滚记录见 `proxy-rs/docs/账号库切换与点测.md`。

需要交给 Agent 自动完成本机打包、替换和清理时，使用
[Agent 本机部署步骤](../../Agent本机部署步骤.md)，其中包含可直接复制的执行授权、命令和验收标准。

## 几个位置先分清

| 位置 | 是什么 |
|---|---|
| `~/cache/AI/kiro-rs/kiro-rs-src/` | 源码，即本目录的上一级。改代码在这里 |
| `~/kiro-rs/config/config.json` | kiro-rs 的运行配置（端口、API Key、Admin Key）。**含真实密钥，别读出明文、别进 git** |
| `~/kiro-rs/data/accounts.sqlite3` | 账号库：所有账号、凭据、额度、统计。**含全部 token** |
| `~/kiro-rs/data/backups/` | 账号库每日自动备份，保留 7 份 |
| `/Applications/Proxy RS.app` | 正在用的 App；内置的 kiro-rs 在 `Contents/Resources/kiro-rs` |
| `~/Library/Application Support/Proxy RS/account-db.json` | 账号库模式开关与路径 |

## 流程

### 1. 本地先验证

```bash
cd ~/cache/AI/kiro-rs/kiro-rs-src
cargo check --all-targets
cargo test --no-default-features   # 全绿
cd admin-ui && pnpm build          # 改了前端时（tsc -b 会做类型检查）
```

### 2. 打包

```bash
cd ~/cache/AI/kiro-rs/proxy-rs
npm run dist:current               # 先构建 kiro-rs 与前端，再打本机架构的 .app
```

**打包前确认工作区干净**（`git status`）：打包用的是工作区里的文件，别人没提交的改动会一起进包。

`npm run dist:current` 和 `npm run dist:mac` 打包前会永久删除旧 `proxy-rs/dist`，
不再积累到废纸篓；需要留存的旧包先另行保存。旧包被占用或无法检查占用时停止打包。
**纯打包不清理 Rust target**，构建失败也保留缓存。

### 3. 安装、校验后清理本包产物

```bash
npm run install:current            # 安装已有包到 /Applications，校验后清理
# 或将第 2、3 步合为一条命令：
npm run deploy:current             # 打包 → 安装 → 校验 → 清理
```

替换正在运行的应用会短暂中断反代；代理执行替换前需获得用户授权。
脚本先用 ditto 复制到 Applications 内的临时目录，核对全包文件内容、执行权限、软链和签名，
再正常退出旧应用并替换，安装后再次核对并请求启动。不会强制杀进程。
复制失败或旧应用未退出时保留旧应用；替换校验失败时恢复旧应用。
成功后永久删除本次安装暂存和旧版备份。启动请求失败时保留备份并显示位置，不清理 target。
系统接受启动请求不等于业务健康检查通过，仍需第 4 步验证。

如果已经手动把同一包拖入 Applications，`npm run install:current` 校验一致后直接清理，
不会重复替换或重启应用。

安装校验通过后：

- 以 `cargo clean --frozen --profile dev/release --package kiro-rs` 分别清理本包
  Debug、Release 编译产物与增量缓存；显式固定本仓库的 target/build 目录。
  保留第三方依赖缓存，下次编译只需重建本包相关产物。
- Cargo 按包清理持有构建锁，等待超过 30 秒则跳过剩余清理。
- 清理最后文件活动超过一天的 `account-store-test-<UUID>`、
  `credential-identity-test-<UUID>` 测试临时目录，保留最近一天的测试数据。
- target 被程序、构建进程或语言服务占用时跳过；仅加载第三方宏库的 Rust 语言服务除外，
  因为这些库会保留。本包库与其他占用仍阻止清理。
- 保留最新 dist 安装包、源码、第三方依赖、运行配置和账号库；缓存清理失败不破坏已安装应用。

打包与安装共用 `build/.mac-package.lock` 防止并发操作；安装另持有
`/Applications/.proxy-rs-install.lock`，防止不同 checkout/worktree 同时替换同一应用。异常中断遗留锁时，
确认相关进程已退出后才移除此空目录。直接运行 `build:mac`、`build:mac:current`
或 `build:kiro-rs` 不触发清理。

### 4. 确认正常

```bash
pgrep -fl "Proxy RS.app/Contents/Resources/kiro-rs"     # 子进程在
lsof -nP -iTCP:12888 -sTCP:LISTEN                       # 只监听 127.0.0.1
curl --noproxy '*' --max-time 5 -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:12888/admin   # 期望 200
```

需要检查受认证 Admin API 时，在进程内读取密钥并发送请求，只输出脱敏结论；
不要把密钥展开到命令行参数，也不要打印完整 API 响应。详见 Agent 本机部署步骤。

`/v1/models` 返回 401 是正常的，那是需要 API Key 的业务接口。

kiro-rs 的日志经 proxy-rs 转存，在 App 的系统日志页按 `kiro-rs` 分类看。

## 几个已经踩过的坑

**dist 的坑。** `admin-ui/dist` 被 gitignore（是构建产物），但 `rust-embed` 在
**编译期**就要读它。所以新克隆的仓库直接 `cargo build` 会失败，报
`function or associated item 'get' not found for this struct` —— 这不是代码坏了，
是缺 dist。先 `cd admin-ui && pnpm install && pnpm build`。
`proxy-rs/scripts/build-kiro-rs.sh` 会先构建前端，不受影响。

**Cargo.lock 的坑。** 根 `.gitignore` 有 `*.lock` 规则会吞掉它，已加
`!kiro-rs-src/Cargo.lock` 例外。二进制项目必须锁依赖，别把这条例外删了。

**上游已断。** 本目录是 `hank9999/kiro.rs` 的 fork 拷贝，移入单仓时断开了 git 关联。
上游有更新只能手工 diff 对，`git pull` 拿不到。

## 号池、凭据与 CLI

账号库里的每个账号都由 kiro-rs 刷新 token、查额度，但只有**入池**的账号才接反代请求。

- proxy 账号卡片上原来的"推送到反代"按钮变成号池开关：云图标常亮表示在池中，再点一次移出。
- Admin 页面默认只列号池中的账号；头部"仅号池 / 全部账号"可以看到库里其它账号并把它们加入号池。
- Admin 的"彻底删除"会把账号从库里删掉，proxy 列表也会消失，且不能用同一账号 ID 重新导入；
  只想停止接单请用"移出号池"。
- 凭据（refresh token / client 信息 / region）由 kiro-rs 独占写入，proxy 的编辑对话框
  里这些字段是只读的；换凭据请重新登录该账号。
- proxy 侧给账号绑定的出口代理会同步给 kiro-rs；解绑时只清除 proxy 自己设过的那份，
  迁移自 `credentials.json` 的账号自带代理保留。

### Kiro CLI 切号

分工：**CLI 当前登录的账号只由 kiro-cli 自己刷新，其余账号由 kiro-rs 刷新**，token 都存在账号库里。
一个账号只能有一个刷新方：refresh token 是一次性的，CLI 大约在过期前 9～10 分钟刷新，
kiro-rs 的阈值是 10 分钟，两边都刷迟早撞车。

- CLI 刷新后，proxy 把它的新凭据交给 kiro-rs 收编（`POST /api/admin/accounts/adopt`）：
  用 CLI 的 access token 查上游 userId，命中库中账号、且比库里新才替换，别的账号的 token
  写不进来；比库里旧就反过来把库里的写给 CLI。
- proxy 每轮对账都把 CLI 当前账号告诉 kiro-rs（`PUT /api/admin/accounts/external-refresh`，
  `/store/info` 的 `externalRefreshCredentialId` 可查）。kiro-rs 对它不做任何刷新：
  token 过期前照常调度，过期后暂停调度（不计失败、不禁用），等 CLI 刷新、收编后自动恢复。
  所以 CLI 长时间不用时，反代会暂时用不到这个账号。
- 直接 `kiro-cli login` 的账号如果也在库里，同样会被认出来；CLI 换成不在库里的账号或退出登录后，
  原来那个账号自动交回 kiro-rs 刷新。
- 对账在账号库变化、每分钟定时、kiro-rs 启动就绪时各跑一次。kiro-rs 的后台巡检首轮推迟 30 秒，
  保证 App 刚打开时先认定 CLI 账号、再开始刷新。标记只在内存里，kiro-rs 重启后由 proxy 重新告知。

`KIRO_CLI_DB_PATH` 可以把 CLI 数据库指到别处，用于联调时不动真实登录状态。
