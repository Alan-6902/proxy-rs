# 抢号报表数据

「抢号监控」页里的报表卡片读的是一份独立的事件流文件。这篇说明它存在哪、存什么、
为什么不复用已有的花费账本，以及想自己拿去分析时怎么读。

## 文件位置

```
<userData>/ksk-hunter-report.jsonl
```

`<userData>` 是 Electron 的 `app.getPath('userData')`：

| 平台    | 路径                                              |
| ------- | ------------------------------------------------- |
| macOS   | `~/Library/Application Support/proxy-rs/`         |
| Windows | `%APPDATA%\proxy-rs\`                             |
| Linux   | `~/.config/proxy-rs/`                             |

报表卡片右上角的「历史文件」按钮会直接在文件管理器里定位到它。抢号还没产生过任何
成果事件时文件不存在，按钮会提示这一点而不是打开空目录。

## 为什么另存一份

抢号本身已经有两处持久化，但都撑不起历史报表：

| 已有数据                        | 保留策略                                  | 为什么不够 |
| ------------------------------- | ----------------------------------------- | ---------- |
| `ksk-hunter.enc` 里的 `spend`   | 只留近 14 天（`SPEND_RETENTION_DAYS`）    | 更早的花费会被裁掉 |
| `ksk-hunter.enc` 里的 `deliveries` | 只留最近 200 条（`MAX_DELIVERY_RECORDS`） | 量大时看不到早期交付情况 |

两者都是「够用就裁」的运行态，裁剪是有意的（避免加密文件无界增长）。报表要的是
**永久保留的成果口径**，所以走独立文件、只追加、不裁剪。

不加密的理由：事件里**不含 KSK 明文、不含脱敏 key、不含站点 token**，没有需要
safeStorage 保护的东西。明文 JSONL 反过来是优点——可以直接 `jq` 拿去做别的分析。
另一个好处是不用挤加密 store 那条 mutation 队列（3 秒一轮的抢号在用它）。

## 记了哪些事件

只记低频的成果节点。3 秒一轮的轮询如果每轮都记，一天就是几万行，且指标会失真。

| `type`            | 什么时候记                                     | 去重方式 |
| ----------------- | ---------------------------------------------- | -------- |
| `restock`         | 某条链接从**无货变有货**的那一刻               | 只记边沿；一批货被连着几十轮发现只算 1 次 |
| `ordered`         | 下单成功，钱已花出去                           | 每单一条 |
| `dead_key`        | 已购但验活不通过（钱花了号不能用）             | 每单一条 |
| `delivered`       | 推送下游成功                                   | 每单一条 |
| `delivery_failed` | 推送**重试耗尽**                               | 只在耗尽时记；6 次重试不算 6 次失败 |
| `blocked`         | 预算 / 余额 / 未知价格拦下了一次自动下单       | 按「本地日期 + 链接 + 原因」去重，同日同因只记 1 条 |

`blocked` 的去重键带日期，所以跨天会自然重新记一次，不需要额外的清理定时器。

## 行格式

一行一个 JSON 对象（JSONL），字段随 `type` 可选：

```json
{"at":1786000000000,"type":"ordered","channel":"kiro_ceo","linkId":"a1b2","linkName":"Kiro CEO · eu","region":"eu-central-1","costUnit":120,"costCny":30,"unitLabel":"CRD"}
{"at":1786000100000,"type":"restock","channel":"kiro_market","linkId":"c3d4","linkName":"Kiro Market · eu","offerCount":2,"region":"eu-central-1"}
{"at":1786000200000,"type":"blocked","channel":"kiro_market","linkId":"c3d4","linkName":"Kiro Market · eu","reason":"global"}
```

| 字段         | 说明                                                                  |
| ------------ | --------------------------------------------------------------------- |
| `at`         | 毫秒时间戳。聚合按**本地自然日**切分，不是 UTC。                      |
| `channel`    | `KskHunterChannel` 枚举值。                                           |
| `linkId`     | 链接 id。链接删掉后仍保留，历史不会因为删链接而消失。                 |
| `linkName`   | 当时的链接名。链接改名后报表按最新一次事件里的名字展示。              |
| `costUnit`   | 该单原币金额。商品没给价格时缺失——**不是 0**，均价计算会跳过这类单。 |
| `costCny`    | 折合人民币元，按下单当时的汇率系数算。                                |
| `unitLabel`  | 下单当时的计价单位。改配置不会改写历史事件。                          |
| `offerCount` | `restock` 专有：这次边沿发现的在售商品数。                            |
| `reason`     | `blocked` 专有：`global` / `channel` / `balance` / `unknown_price`。   |

解析容错：单行坏掉（写盘中途断电）只丢那一行；认不出 `type` 或 `channel` 的行丢弃。
整份文件读不出来时按空历史处理——报表是观测数据，不该阻塞抢号。

## 报表展示的窗口

事件**全量保留**，但页面只展示所选窗口（默认近 30 天，可切近 7 天）。窗口外的事件
不计进曲线与明细，但仍计进卡片底部的「已攒 N 条事件，最早 …」——这样才能看出历史
攒了多久。

聚合逻辑在 `src/shared/hunterReport.ts` 的 `summarizeHunterReport`，是纯函数，
不依赖 Electron，可以直接拿来对着自己导出的 JSONL 跑。

## 自己查数据

```bash
cd ~/Library/Application\ Support/proxy-rs

# 今天买了几个号、花了多少
jq -s '[.[] | select(.type=="ordered")] | {单数: length, 花费: (map(.costCny // 0) | add)}' ksk-hunter-report.jsonl

# 各渠道放货次数
jq -r 'select(.type=="restock") | .channel' ksk-hunter-report.jsonl | sort | uniq -c

# 放货时段分布（本地小时）
jq -r 'select(.type=="restock") | .at' ksk-hunter-report.jsonl \
  | while read -r ms; do date -r $((ms/1000)) +%H; done | sort | uniq -c
```

## 清理

文件按设计只增不减。事件很小（约 150 字节一条）且只记成果节点，正常用一年也在
万级行数、几 MB 量级。真要清理就直接删掉这个文件，应用会按空历史重新开始攒——
但那段历史无法恢复，删之前先备份。
