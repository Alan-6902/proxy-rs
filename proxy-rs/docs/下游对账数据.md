# 下游对账数据

「下游对账」页要回答一个问题：**这段时间我交给下游哪些号、下游拿它们烧了多少积分**，
用来跟下游对账收款。这篇说明数据存在哪、两种口径分别怎么算、CSV 每列什么含义，
以及为什么 CSV 里敢放完整 KSK。

## 数据存在哪

| 文件 | 内容 | 加密 | 保留 |
| ---- | ---- | ---- | ---- |
| `<userData>/ksk-delivery-ledger.enc` | 交付记录（含完整 KSK）+ 每日结算定稿 | ✅ safeStorage | 交付记录永久；结算定稿 90 天 |
| `<导出目录>/downstream-YYYY-MM-DD.csv` | 每日对账宽表（含完整 KSK） | ❌ 明文 | 永久，只增不减 |

`<userData>` 是 Electron 的 `app.getPath('userData')`：

| 平台    | 路径                                      |
| ------- | ----------------------------------------- |
| macOS   | `~/Library/Application Support/proxy-rs/` |
| Windows | `%APPDATA%\proxy-rs\`                     |
| Linux   | `~/.config/proxy-rs/`                     |

`<导出目录>` 默认是 `<userData>/downstream-csv/`，可以在对账页点「改目录」换成任意
绝对路径。页面上的「打开目录」会直接在文件管理器里打开它。

## 为什么另存一份

抢号侧已经有三份数据，都答不了对账的问题：

| 已有数据 | 是什么 | 为什么不够 |
| -------- | ------ | ---------- |
| `ksk-hunter.enc` 的 `deliveries` | 运行态推送队列 | 只留最近 200 条（`MAX_DELIVERY_RECORDS`），会被裁掉 |
| `ksk-hunter-report.jsonl` | 抢号成果事件流 | 刻意不含 key（那是明文文件），看不出交的是哪个号 |
| `ksk-hunter-ledger.json` | 抢号台账 | **采购**维度：没有交付时刻，也不区分交付成功与验活判死 |

所以交付账本单独一份，只在**推送下游成功**那一刻记一条。验活判死（钱花了号没交出去）
与推送重试耗尽都不记——它们不是收款依据，混进来会让对账多收钱。

**为什么必须加密**：这份文件里有完整 KSK 明文。另外两份观测数据只有脱敏 key，
明文落盘无所谓；这里明文落盘等于把已交付的号裸放在磁盘上。

## 两种口径

页面和 CSV 同时给「交付号数」和「下游烧掉的积分」两组数，按哪个收款都能对上。
两者的时间口径**不一样**，这点最容易搞混：

### 交付数与花费：精确的自然日

`deliveredAt` 是精确时间戳，按本地自然日左闭右开切分。前一天 23:59:59 和次日
00:00:00 都不算进今天。花费记在**交付那天**，往期号后续烧积分不会重复计花费。

### 积分：区间口径

上游只给累计消耗值（台账的 `usedCredits` 就是它，且已经处理过按月重置的结转）。
要得到「某个自然日烧了多少」必须在日界那一刻正好采样，而桌面应用可能整天没开。
所以积分按**上次结算到本次结算**的区间记账：

```
本区间积分 = 台账当前累计 − 该号上次结算时的锚点（settledCredits）
```

结算 tick 每 30 分钟一轮，正常情况下区间紧贴日界，误差在半小时内。
**应用关了几天再打开**则会把那几天并成一个长区间，记到最早那个未结算日。
CSV 里带「积分区间起 / 积分区间止」两列，跨度多大一眼可见，不假装是单日。

### 页面上的三种状态

| 状态 | 积分怎么来 | 会不会变 |
| ---- | ---------- | -------- |
| 已定稿 | 读结算记录里的历史增量 | 不会再变 |
| 今天 · 未定稿 | 按当前台账实时估算 | 会随消耗增长 |
| 过去某天 · 未定稿 | **留空** | 结算后才有数 |

过去某天未定稿时刻意不显示实时估算值：待结算的积分会被记到最早那个未结算日，
其余日子归 0。给每个未定稿的过去日都显示同一个实时值，等 tick 跑完就变成 0，
看起来像账目自己变了。留空 +「未定稿」标记才是实话。想立刻有数就点「立即结算」。

### 积分显示「—」是什么意思

台账里查不到这个号（台账被清空过、或号还没入库）。**这是「未知」，不是 0**——
显示成 0 会让对账少收钱。此时结算也不会推进这个号的锚点，等台账恢复后能补上，
不会永久丢账。

## 每日 CSV

一行一个号。行集是**两个集合的并**：当天交付的号，加上当天有积分增量的号
（可能是更早交付的，标「是否当日交付 = 否」）。

举例：一个 8 月 1 日交付的号，8 月 5 日还在烧积分，就会同时出现在
`downstream-2026-08-01.csv`（是否当日交付=是）和 `downstream-2026-08-05.csv`（=否）。

| 列 | 说明 |
| -- | ---- |
| `日期` | 这份 CSV 对应的本地自然日 |
| `交付时刻` | 本地时间 `YYYY-MM-DD HH:mm:ss` |
| `交付小时` | 本地小时 `00`-`23`，对应页面上的柱状图 |
| `完整Key` | Kiro API Key 明文，跟下游精确对账用 |
| `脱敏Key` | `ksk_...abcd`，页面上只显示这个 |
| `Region` | AWS 区域 |
| `渠道` | `KskHunterChannel` 枚举值 |
| `链接` | 交付时的链接名 |
| `分组` | 交付时所属账号分组的**当前**名字；未分组或分组已删时为空 |
| `买入价` / `计价单位` / `买入价CNY` | 该单成本；商品没给价格时为空（**不是 0**） |
| `是否当日交付` | `是` / `否`。`否` = 往期号，这天仍在烧积分 |
| `当日新增积分` | 本区间新增消耗；台账查不到时为空 |
| `积分区间起` / `积分区间止` | 上面那个数覆盖的时间区间 |
| `累计消耗积分` | 台账里该号从买入到现在的总消耗 |
| `号状态` | `alive` / `retired` / `dead_on_arrival` |

编码是 **UTF-8 带 BOM**，Excel 双击直接打开不乱码。文件权限 `0o600`（仅本人可读）。

同一天重复导出会**覆盖**同名文件，所以「白天手动导一次、午夜自动再结算一次」
不会留下两份互相矛盾的文件。

## ⚠️ 完整 KSK 的安全须知

CSV 里带完整 key 是刻意的设计（下游握的是完整 key，脱敏后对不上），代价是：

- **这份文件泄露等于号被直接拿走。** 它是磁盘上唯一存在 KSK 明文的地方。
- **导出目录若指向 iCloud、坚果云等同步盘，号会被上传到云端**，且云端可能保留
  历史版本，本地删掉也未必消失。
- 应用内其它地方一律只显示脱敏 key：页面、日志、错误提示都不会回显明文。
- 交付账本本身走 safeStorage 加密，只有 CSV 是明文。

拿 CSV 去对账之后，建议放在加密卷或本机目录，不要长期留在共享位置。

## 结算调度

后台每 30 分钟检查一次有没有未结算的**过去**日期，有就逐日补齐：先写 CSV，
再落定稿记录并推进积分锚点。

- **只结算已经过去的自然日。** 今天还在产生交付与消耗，定稿了数字就不再变，
  会漏掉当天剩下的部分。
- **先写 CSV 再推进锚点。** 反过来的话导出失败就再也导不出这一天了——锚点已推进，
  积分增量算不回来。
- **关机几天再打开会自动补齐**，一次补多天，每天各自一份 CSV。
- 不做午夜定时：那套要处理系统睡眠、时区变更、夏令时，脆且难验证；tick + 补齐
  天然覆盖所有这些情况。

页面上的「立即结算」按钮就是手动触发一轮补齐，不必等下一轮 tick。
「导出这天的 CSV」是纯读操作，不推进锚点，可以随便点。

## 自己查数据

CSV 是普通文本，直接拿工具处理：

```bash
cd ~/Library/Application\ Support/proxy-rs/downstream-csv

# 8 月总共交付多少个号
awk -F, 'FNR>1 && $13=="是"' downstream-2026-08-*.csv | wc -l

# 8 月下游总共烧了多少积分
awk -F, 'FNR>1 {sum+=$14} END {print sum}' downstream-2026-08-*.csv

# 某一天按分组汇总交付数
awk -F, 'FNR>1 && $13=="是" {print $9}' downstream-2026-08-10.csv | sort | uniq -c
```

交付账本是加密的，没法直接读；页面上的报表就是它的视图。聚合逻辑在
`src/shared/downstreamSettlement.ts`，是纯函数、不依赖 Electron，可以直接
拿来对着自己的数据跑。

## 清理

CSV 按设计只增不减，一天一个文件、一行几百字节，正常用一年也就几 MB。
真要清理就直接删文件——但那是对账依据，删之前先确认已经跟下游结清。

交付账本没有清理入口：它是收款依据，裁掉就等于账目缺一块。
