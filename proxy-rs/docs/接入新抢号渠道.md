# 接入新抢号渠道

给「抢号监控」页加一个新的商品聚合站点。照着做，5 处改动 + 1 组测试。

> **前置**：先拿到该站点的**真实响应样例**——商品列表一份、下单成功一份。
> 拿不到就别猜字段名：猜错的表现是「一直显示无货」，而不是报错，很难排查。
> 没有样例时应当停下来问用户要，不要凭站点名推测字段。

## 术语

| 词                 | 含义                                                                         |
| ------------------ | ---------------------------------------------------------------------------- |
| **渠道 / channel** | 一个商品聚合站点，如 Kiro Market。代码里是 `KskHunterChannel` 枚举值。       |
| **链接 / link**    | 用户在 UI 里配的一条监控项。一个渠道可以有多条链接（不同区域、不同 token）。 |
| **商品 / offer**   | 列表接口返回的一个可买条目，归一化成 `KskHunterOffer`。                      |

渠道决定**怎么解析**，链接决定**查哪个地址**。新增站点改渠道，用户加地址改链接。

## 第 1 步：加渠道枚举

`src/shared/kskHunter.ts`：

```ts
export const KSK_HUNTER_CHANNEL = {
  KIRO_MARKET: 'kiro_market',
  KIRO_CEO: 'kiro_ceo',
  KIRO_DROP: 'kiro_drop',
  KIRO_VAULT: 'kiro_vault' // ← 新增
} as const

export const KSK_HUNTER_CHANNEL_LABEL: Record<KskHunterChannel, string> = {
  [KSK_HUNTER_CHANNEL.KIRO_MARKET]: 'Kiro Market',
  [KSK_HUNTER_CHANNEL.KIRO_CEO]: 'Kiro CEO',
  [KSK_HUNTER_CHANNEL.KIRO_DROP]: 'Kiro Drop',
  [KSK_HUNTER_CHANNEL.KIRO_VAULT]: 'Kiro Vault' // ← 新增
}
```

**枚举值一旦发布就不能改**：它会被写进用户的加密配置文件。改了等于用户已配的链接
全部认不出渠道，会被 `normalizeChannel` 静默回落成 Kiro Market，解析全错。
改显示名（label）随便改，那只影响 UI 文案。

## 第 2 步：加计费默认值

同一个文件里，`DEFAULT_KSK_HUNTER_BILLING` 加一项：

```ts
export const DEFAULT_KSK_HUNTER_BILLING: Record<KskHunterChannel, KskHunterChannelBilling> = {
  // ...
  [KSK_HUNTER_CHANNEL.KIRO_VAULT]: {
    unitLabel: 'CNY',
    cnyPerUnit: 1,
    dailyLimitUnit: 0,
    lowBalanceThresholdUnit: 0
  }
}
```

`unitLabel` 填该站点的计价单位（人民币填 `CNY`，积分制填 `积分`，点数制填 `CRD` 之类）。
其余三个字段都留默认（1 / 0 / 0），**汇率、上限与余额阈值都由用户在 UI 里填**——
兑换比会变，硬编码在代码里迟早过期。

注意 `dailyLimitUnit` 与 `lowBalanceThresholdUnit` 的单位都是**该渠道的原币**（不是人民币）：
用户脑子里的预算就是「每天最多 500 积分」，按人民币填得自己先乘一遍汇率。
`cnyPerUnit` 只用于跨渠道汇总展示。

> **为什么系数默认 1 而不是 0**：填 0 会让该渠道所有花费算成 ¥0，
> 每日上限判断彻底失效、无限狂买。`normalizeChannelBilling` 对非正系数一律回落到 1，
> 宁可记错账也不能让熔断失效。

余额查询地址不在这里配：它是**渠道级密钥**，由用户在 UI 里填（存进加密 store 的
`secrets.balanceUrls`），新增渠道后该渠道的输入框会自动出现。余额字段用
`parseHunterBalance` 递归识别（认 `balance` / `points` / `credit` / `remain` 等名字），
通常不需要为新渠道改动。

## 第 3 步：写列表解析

同一个文件里，照抄一个现成的改字段名。目标是产出 `KskHunterOffer`：

```ts
/** Kiro Vault：商品在 result.items 下，库存字段是 available_count。 */
function parseKiroVaultOffers(payload: unknown): KskHunterOffer[] {
  return readOfferArray(payload).flatMap((item) => {
    if (!isRecord(item)) return []
    const goodsId = readString(item.sku ?? item.id)
    if (!goodsId) return [] // 没有商品 ID 就没法下单，直接丢弃
    return [
      {
        goodsId,
        title: readString(item.name ?? item.title),
        region: resolveOfferRegion(item.area, item.tag, item.name),
        stock: resolveStock(item.available_count, item.stock),
        price: readNumber(item.price)
      }
    ]
  })
}
```

注册进去：

```ts
export function parseChannelOffers(channel: KskHunterChannel, payload: unknown): KskHunterOffer[] {
  assertBusinessOk(payload)
  switch (channel) {
    // ...
    case KSK_HUNTER_CHANNEL.KIRO_VAULT:
      return parseKiroVaultOffers(payload)
  }
}
```

### 可复用的工具函数

**先用这些，不要自己写解析。** 它们已经处理了各站点的常见花样：

| 函数                          | 作用                                                                                                                                                        |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `readOfferArray(payload)`     | 从 `data` / `list` / `items` / `goods` / `products` / `result` 等包装层里挖出商品数组，也支持两层嵌套（`data.list`）和顶层就是数组。找不到时抛错。          |
| `resolveOfferRegion(...候选)` | 按顺序认区域。先找完整格式（`eu-central-1`），再退回短代号（`#key-eu` → `eu-central-1`）。认不出返回 `''`。**把所有可能含区域的字段都传进去**，它自己挑。   |
| `resolveStock(...候选)`       | 归一化库存。认数字、`"3"`、boolean，也认「售罄 / 缺货 / sold out」→ `0` 和「有货 / in stock」→ `1`。                                                        |
| `readString` / `readNumber`   | 容错取值。`readNumber` 对缺失字段返回 `undefined` 而非 `0`（价格显示成 ¥0.00 会误导人）。                                                                   |
| `assertBusinessOk(payload)`   | 已在 `parseChannelOffers` 里统一调过，**别在自己的函数里重复调**。它认 `code: 0`/`200`/`'ok'`/`'success'`/`success: true`；没有 `code` 字段的站点自动跳过。 |

### 硬约束

- **不要在这里过滤库存和区域**。返回所有商品，`stock: 0` 的也返回。
  过滤由 runner 统一做（它要按用户配的区域白名单筛），你在这里筛会让
  「当前有货」的状态显示不出来。
- **不要在这里发请求**。解析函数必须是纯函数，只做 payload → offer[]。
- **解析不出来就抛错**，别返回空数组。空数组等于「查到了但没货」，
  会把接口挂掉伪装成正常无货，用户永远等不到通知。
- **`price` 一定要正确解析**，且必须是该站点的**原始计价数字**（不要自己换算成人民币，
  换算由 `cnyPerUnit` 做）。价格解析错的后果比字段名错更严重：
  - 解析不到 → `price` 为 `undefined` → 默认配置下**该商品永远不会被自动下单**
    （链接卡片会提示「商品未提供价格」）
  - 解析成偏小的值 → 每日上限形同虚设，可能超预算买入

## 第 4 步：加下单请求体

```ts
export function buildOrderRequestBody(
  channel: KskHunterChannel,
  offer: KskHunterOffer
): Record<string, unknown> {
  switch (channel) {
    // ...
    case KSK_HUNTER_CHANNEL.KIRO_VAULT:
      return { sku: offer.goodsId, qty: 1 }
  }
}
```

只改参数名。**数量恒为 1**：下游一次只回答要不要一个号，买多了没人接。

请求固定是 `POST` + `Content-Type: application/json`，地址是用户配的下单 URL
（token 在 URL 的 query 里）。**如果新站点需要额外请求头或非 JSON 体，
先停下来告诉用户**——那要改 `hunterRunner.ts` 的 `fetchJson`，属于超出本文档的改动。

### 下单响应不用管

`parseOrderedCredential` 是**渠道无关**的：它递归搜索响应里第一个 `ksk_` 开头的字符串
（最多 6 层），同层就近认区域，认不出再用下单那条商品的区域兜底。也支持
`ksk_xxx----eu-central-1` 卡密文本。

所以新渠道通常**不需要**改它。只有一种情况要动：响应里有多个 `ksk_` 字符串且第一个不是
你要的那个。真遇到了在 `findCredentialInPayload` 的字段名列表里加你的字段名
（当前认 `key` / `ksk` / `apiKey` / `api_key` / `kiroApiKey` / `card` / `secret`）。

## 第 5 步：写测试

`test/integration/ksk-hunter.test.ts` 的 `describe('站点响应解析')` 里加一条。
**用真实响应样例，别用自己编的**：

```ts
it('Kiro Vault：读 available_count 与 area', () => {
  const offers = parseChannelOffers(KSK_HUNTER_CHANNEL.KIRO_VAULT, {
    code: 0,
    result: { items: [{ sku: 'v1', name: 'Kiro Key', area: 'eu', available_count: 2, price: 40 }] }
  })
  expect(offers).toEqual([
    { goodsId: 'v1', title: 'Kiro Key', region: 'eu-central-1', stock: 2, price: 40 }
  ])
})
```

至少覆盖三种情形：

1. **有货 + 区域能认出** — 主路径
2. **售罄** — 确认 `stock` 归一化成 `0`（站点用 `"售罄"` 还是 `0` 表达？）
3. **下单请求体字段名** — 加进现有的 `buildOrderRequestBody` 那条 `it` 里

顺带在 `describe('抢号调度')` 里跑一次全链路，能同时验证 runner 的过滤逻辑对新渠道生效。

## 排查

| 现象                                      | 大概率原因                                                                                                                                                                        |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 一直显示无货，但站点确实有货              | 库存字段名猜错，或 `readOfferArray` 没找到数组（此时会抛错，看链接卡片上的错误提示）                                                                                              |
| 有货但不下单                              | 三种可能：① 区域认不出（`region` 为 `''`，命中不了白名单），把更多字段传给 `resolveOfferRegion`；② 商品无价格且未开「允许未知价格下单」；③ 当日预算已用尽（页面顶部会有红色横幅） |
| 卡片上报「商品站点接口必须使用 HTTPS」    | 列表地址填了 `http://`。硬约束，不放行                                                                                                                                            |
| 下单成功但报「没有找到 ksk\_ 开头的密钥」 | 响应嵌套超过 6 层，或 key 字段名不在识别列表里                                                                                                                                    |
| 报「下单成功但无法确定区域」              | 响应和商品都没有可识别区域。检查该商品的 `region` 解析                                                                                                                            |
| 卡片上报「商品未提供价格」                | `price` 没解析出来。检查价格字段名；或临时开「允许未知价格下单」（花费会记 ¥0）                                                                                                   |
| 今日花费统计明显偏小 / 偏大               | 该渠道的「1 单位 = ? 元」填错了。原币金额在花费卡片上能看到，用它核对                                                                                                             |
| 明明没花到上限却停了自动下单              | 熔断按「已花 + 这单」判断。上限 20、已花 15、单价 10 时买不下这一单，属正常行为                                                                                                   |
| 卡片上报「余额不足」但账户里其实有钱      | 余额响应的字段名不在 `parseHunterBalance` 的识别列表里，或嵌套超过 6 层                                                                                                           |
| 开了余额检查却从不按余额拦单              | 余额查询失败时按「不拦」处理（站点抖一下不该停掉抢号）。看卡片上的余额查询失败提示                                                                                                |

链接卡片上的 `lastError` 是排查入口，它记录了该链接最近一次查询失败的原因。

## 别做的事

- **改已发布的枚举值** — 会让用户已配的链接认不出渠道，也会让历史花费记录被丢弃
- **在解析里把价格换算成人民币** — 换算由 `cnyPerUnit` 做，你换算了会被二次乘算
- **把 `cnyPerUnit` 默认值设成 0** — 花费全算成 0，每日上限彻底失效
- **在解析函数里过滤库存/区域** — runner 统一做，你筛了状态就显示不出来
- **解析失败返回空数组** — 把故障伪装成无货
- **调低 `KSK_HUNTER_POLL_INTERVAL_SECONDS`** — 3 秒是和单链接防重入配套的
  （请求超时 10 秒 > 轮询间隔，靠 `inFlightLinks` 跳过未返回的链接）。改小会给站点叠并发
- **一轮买多个** — 下游一次只回答要不要一个
- **在日志或错误信息里写 `key` 明文** — 全链路都做了脱敏，别开口子
